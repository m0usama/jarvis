Now for your learning moment: queues and event-driven design.

In basic script automation, execution flows sequentially. Script A calls Script B, which calls Script C. If Script B fails or takes twenty seconds, the entire workflow halts. In event-driven design, components do not call each other directly. Instead, when an action occurs, a system produces an event payload and places it into a central queue. Independent consumer processes listen to that queue, pick up messages, and process them at their own pace.

Imagine your job card print automation. In a synchronous design, when a user uploads a job card photo from their phone, the web API holds the connection open while the vision model processes the image, updates the Google Sheet, and sends the print file to the printer. If the vision model takes ten seconds, the mobile app hangs, and if the network drops, the request fails entirely.

In an event-driven architecture, the web API receives the photo, writes a brief message into a queue containing the file location, and immediately responds to the phone with a success status. A background worker picks up the message from the queue, runs the vision model, updates the sheet, and triggers the print workflow. If the printer is busy or offline, the job stays safely in the queue until the worker retries it, without breaking the web interface or losing data.

In production data and software engineering, event-driven architecture with queues guarantees reliability, decouples heavy processing from user interfaces, and allows systems to scale horizontally by simply adding more worker processes.
