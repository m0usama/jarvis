That brings us to today's learning moment: SQL indexing and query plans.

When a database executes a query, it can either scan every single row in a table to find matching data, known as a full table scan, or use an index to jump straight to the correct records. An index is a dedicated data structure, usually a B-tree, that keeps a sorted pointer to specific table columns. Searching an unindexed column takes linear time, whereas searching an index takes logarithmic time, making searches drastically faster as datasets grow. However, indexes are not free; they take up extra disk space and slightly slow down insert and update operations because the index must be updated every time data changes.

To see how this works in practice, imagine a print job database with one hundred thousand records. If you query for all jobs belonging to a specific customer without an index, the database engine executes a table scan, reading all one hundred thousand rows off the disk. When you run EXPLAIN QUERY PLAN before your SELECT statement, the database engine returns an execution report explicitly stating SCAN TABLE. Once you execute CREATE INDEX on the customer identifier column, running EXPLAIN QUERY PLAN again returns SEARCH TABLE USING INDEX. Instead of inspecting every row, the database performs a few pointer lookups and returns the result in a fraction of a millisecond.

In real-world engineering, query plans are the primary tool for diagnosing slow backend APIs and ETL pipelines. When a FastAPI endpoint or automated reporting script starts timing out under heavy load, inspecting the query plan reveals instantly whether missing indexes or inefficient joins are causing the failure. Knowing how to analyze and fix query execution plans ensures your automated pipelines and backend systems remain responsive as data volume scales.
