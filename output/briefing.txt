That brings us to today's learning moment: retries, backoff, and idempotency in automations. 

When an automated script talks to an external system, whether an LLM provider, a cloud database, or a print server, network hiccups and rate limits will inevitably cause transient failures. A naive script simply fails immediately, halting the workflow. A slightly better script retries right away. However, retrying immediately can overwhelm a struggling server in what is known as a thundering herd problem. 

To fix this, engineers use backoff, specifically exponential backoff with jitter. Instead of retrying instantly, the system waits for one second, then two, then four, adding a small random delay each time to prevent synchronized traffic spikes. 

However, retrying safely requires idempotency. An idempotent operation is one that produces the exact same outcome whether executed once or ten times. Reading a record is naturally idempotent; charging a payment or inserting an order row is not. If your network fails right after the remote server processes an order but before it sends back a confirmation, a blind retry could create a duplicate charge. 

In real engineering work, you implement idempotency using unique keys. When your automation issues an action, it attaches a unique idempotency key, such as a hash of the job card details or a timestamped UUID. The receiving system checks whether it has already handled that specific key. If it has, it safely returns the original success message without executing the side effect twice. Understanding and pairing exponential backoff with strict idempotency keys is what separates brittle weekend scripts from production-grade enterprise automations.
