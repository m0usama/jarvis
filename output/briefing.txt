Now for your learning moment on evaluating LLM and agent outputs. 

In classical software engineering, you test code deterministically: input two and two, assert the output equals four. When an LLM or an autonomous agent is part of your system, outputs are non-deterministic, making simple equality assertions useless. Evaluation is the engineering discipline of measuring whether generative and agentic outputs meet strict standards of accuracy, relevance, and safety, systematically and at scale.

Evaluation splits into two core approaches: component evaluations and end-to-end evaluations. For simple structured tasks, you use deterministic heuristics. For example, if an agent extracts print specifications, you do not ask another model whether the extraction was good; you check if the JSON conforms to your Pydantic schema, whether the stock weight is a valid positive integer, and whether the job ID matches your database format. 

For open-ended outputs, such as summarising a technical report or deciding the next tool to call in an agent loop, you use reference-based metrics or model-graded evaluation. Model-graded evaluation involves writing a strict, rubrics-based prompt for an evaluator model, instructing it to inspect the original input, the agent's retrieved context, and the final response, scoring specific criteria like faithfulness, retrieval relevance, and answer correctness on a binary pass or fail scale.

In professional engineering environments, evaluation is not an afterthought run manually in a notebook. It lives inside automated CI/CD pipelines. Every time you change a prompt, alter chunking logic in RAG, or update a tool definition, your automated evaluation suite runs against a curated evaluation dataset. If faithfulness drops below a required threshold or tool call precision regresses, the deployment is blocked. Treating model outputs as verifiable, measurable data streams rather than magic text is what separates professional AI engineering from prompt tinkering.
